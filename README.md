# Adaptive Multiprototype Gaussian Prototypical Network (AMGPN)

Research implementation of **Adaptive Multiprototype Gaussian Prototypical Network for Few-Shot UAV Spectrogram Classification**.

AMGPN addresses few-shot classification of UAV radio-frequency spectrograms. It initializes one Gaussian prototype per support sample and consolidates similar prototypes through graph connected components, preserving distinct within-class modes without fixing the number of prototypes in advance.

**Published in IEEE Internet of Things Journal**, vol. 13, no. 17, pp. 41223–41236, 2026. [Paper DOI: 10.1109/JIOT.2026.3711080](https://doi.org/10.1109/JIOT.2026.3711080).

This repository contains the model implementation, comparison methods, ablation variants, evaluation utilities, and research notebooks. Experimental settings are supplied through an external configuration file. The repository includes empty configuration templates, but does not distribute private settings, datasets, trained weights, or historical experiment outputs.

## Method

AMGPN uses episodic meta-learning. Each episode contains a labeled support set and a query set drawn from the same episode classes.

1. **Feature and precision extraction.** A ResNeXt-style backbone produces an embedding and precision features for each spectrogram.
2. **Instance-level initialization.** Each support embedding becomes the mean of an initial Gaussian prototype, avoiding iterative clustering during initialization.
3. **Graph-based adaptive merging.** Within each class, pairwise prototype distances determine graph edges. Connected components are merged by averaging their prototype means and precision matrices.
4. **Query classification.** A query is scored against the nearest prototype in each class using Mahalanobis distance.

For a support sample $x_{c,j}$, the initial prototype is defined by

$$
\mu_{c,j}=v_{c,j},\qquad P_{c,j}=\operatorname{diag}(1+\operatorname{softplus}(s_{c,j})),
$$

where $P_{c,j}$ is a **precision matrix**. The pairwise distance used to construct the merging graph is

$$
d(p_i,p_j)=\sqrt{(\mu_i-\mu_j)^\top\frac{P_i+P_j}{2}(\mu_i-\mu_j)}.
$$

The threshold defines graph connectivity, and connected components determine the final prototype count. The distance from a query embedding $z_q$ to class $c$ is

$$
D(z_q,c)=\min_m\sqrt{(z_q-\mu_c^m)^\top P_c^m(z_q-\mu_c^m)},\qquad
P(y=c\mid z_q)=\operatorname{softmax}_c(-D(z_q,c)).
$$

The implementation retains the algorithm's mathematical constants, tensor operations, and numerical stability terms. Experiment-specific settings are loaded externally.

## Published Results

The following accuracies are reported in the published paper. They are not results generated by a fresh execution of this repository.

| Dataset | Setting | AMGPN accuracy | Evaluation |
| --- | --- | --- | --- |
| DroneRFb-Spectra | 8-way 10-shot | 96.3% | Episodes constructed from classes held out from meta-training |
| RFUAV | 8-way 10-shot | 86.1% | Direct transfer of a model meta-trained on DroneRFb-Spectra |

RFUAV evaluation keeps the feature extractor and learned parameters fixed. Support samples are used only to construct prototypes at inference time, without RFUAV fine-tuning or dataset-specific hyperparameter revalidation. See the paper for confidence intervals, baseline comparisons, ablations, and efficiency measurements.

## Dependencies

The configuration loader requires Python 3.9 or later. Dependencies are listed from source imports; the original experiment environment is not supplied as a verified version lock. Install a PyTorch build suitable for your device and execution environment.

From the repository root:

```bash
python -m pip install -r requirements.txt

# For notebooks, additional baselines, profiling, or dataset preparation:
python -m pip install -r requirements-optional.txt
```

Dataset preparation, training, evaluation, and plotting are separate workflows. Installing dependencies does not start them.

## External Configuration

`private_config.example.json` contains configuration keys with `null` values. It contains no actual experiment values. Create a configuration file **outside the repository**, then fill the entries required by your selected workflow.

```bash
mkdir -p ../amgpn-private
cp private_config.example.json ../amgpn-private/config.json
chmod 600 ../amgpn-private/config.json

# Fill the required entries before running a workflow.
export AMGPN_PRIVATE_CONFIG="$(cd ../amgpn-private && pwd)/config.json"

# List configuration names and types without displaying their values.
python private_config.py --list-keys --scope GPN_V4_adaMulti_clean.py

# Validate settings without loading a model or dataset.
python private_config.py --check --scope GPN_V4_adaMulti_clean.py
```

Keys identify their source file, class or function, and, for notebooks, cell index. Suffixes such as `__2` distinguish repeated configuration locations within a scope. Configurable values cover episode sampling, optimization, training budgets, preprocessing, network dimensions, prototype merging, and dataset/checkpoint locations.

`--scope` checks only keys with the specified prefix. A complete workflow also needs the settings used by its dataset, loss, and other imported modules. Running `--check` without a scope checks the entire template, including historical variants. You only need to populate settings used by the workflow you intend to run.

Explicit function arguments take precedence over external defaults. Experiment defaults are resolved when their functions are called. Missing values, `null` entries, and incorrect types produce an error identifying the configuration key. The loader rejects private configuration files located inside the repository.

For example, the core model and trainer can be initialized as follows after supplying the required configuration:

```python
from GPN_V4_adaMulti_clean import GPN_Optimized, GPNTrainer

model = GPN_Optimized()
trainer = GPNTrainer(
    model=model,
    device="cpu",  # Select a device available in your environment.
    use_Mdistance=True,
    use_multi=True,
)
```

This example illustrates initialization only. Training and evaluation also require prepared datasets, episode samplers, data loaders, and matching configuration. Empty templates are insufficient to reproduce the published results.

## Data and Workflows

The dataset loaders expect two-dimensional `.npy` spectrograms organized into class directories:

```text
<external-data-root>/
├── <integer-class-id>/
│   ├── <sample>.npy
│   └── ...
└── ...
```

Class directory names must be convertible to integers. Each selected class needs enough samples for the configured support and query sets. Training and test classes must be disjoint; method comparisons should use the same class partitions and evaluation episodes.

1. Prepare spectrograms using the dataset notebooks and configure an accessible external data location.
2. Select a workflow and its matching modules, and supply their required settings.
3. Train the selected model and save checkpoints outside the repository.
4. Configure the corresponding checkpoint location and run evaluation or ablations.
5. Use the analysis and plotting utilities with results from that execution.

Launch notebooks from the repository root so project modules remain importable:

```bash
python -m jupyterlab
```

Stored notebook outputs are cleared in this source distribution. Keep generated checkpoints, experiment reports, and logs outside the repository. Runtime outputs may contain configuration values or paths; they are not automatically sanitized.
